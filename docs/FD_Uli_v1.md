## 2. 系统本质说明
- 本产品在工程上本质是：双人协作工作流系统 + 若干 LLM 分析节点。
- 为保证稳健性并减少幻觉，流程控制必须由后端完成，AI 不得自动推进业务状态。

### 2.1 职责拆分
- 后端系统负责：状态流转（谁可以做什么）、数据存储（事实/记录/分析结果）、权限控制（哪些数据共享）、通知推送、决定何时调用 AI。
- LLM 负责：文本整理、观点抽取、冲突分析、建议生成。
- LLM 不负责：记忆持久化、状态管理、流程决策、数据存储。

## 3. 角色、对象与全局规则
### 3.1 角色与权限
- User A：事件发起方。
- User B：事件参与方。
- System：状态机执行者、权限和数据守护者。
- LLM Service：文本处理服务。

权限原则：仅绑定关系双方可见共享事件与复盘；私有分析会话仅本人可见。

### 3.2 核心对象
- Event：冲突事件主对象。
- Snapshot_A：A 确认后的冻结事实快照（不可变）。
- Snapshot_B：B 确认后的冻结事实快照（不可变）。
- JudgeResult：裁判分析结果（生成后可读，禁止被后续对话覆盖）。
- PrivateSession：个人私有分析会话。

### 3.3 事件状态机
Event.status（枚举值均为小写，对应代码 `constants/enums.py` 中的 `EventStatus`）：
- `draft`：草稿/私有阶段。
- `waiting_b`：A 已确认，等待 B 处理。
- `judged`：裁判结果已生成。
- `reviewed`：已沉淀复盘（枚举已定义，业务流转待实现）。
- `closed`：事件关闭（枚举已定义，业务流转待实现）。

合法流转：
- `draft` -> `waiting_b` -> `judged`（已实现，见 `services/event_service.py`）
- `judged` -> `reviewed` -> `closed`（待实现）

## 4. 大模块一：登录注册模块（用户名+密码，P0）

### 4.1 功能目标
- 提供最小可用账号体系：注册、登录、登出、token 刷新。

### 4.2 注册功能设计
- 输入：username、password、confirmPassword。
- 前端：格式校验、两次密码一致校验。
- 后端：用户名唯一校验、密码哈希存储、创建用户。
- 成功：返回用户基本信息（可选自动登录）。
- 失败：用户名已存在、参数不合法、系统异常。

### 4.3 登录功能设计
- 输入：username、password。
- 点击登录后流程：
  1. 前端发起登录请求并进入 loading。
  2. 后端按用户名查询用户。
  3. 进行密码哈希比对。
  4. 校验账号状态（active/locked/disabled）。
  5. 通过后签发 access_token + refresh_token。
  6. 记录登录日志。
- 成功：前端保存令牌，跳转主页。
- 失败：统一返回"用户名或密码错误"或状态类错误。

### 4.4 登出与刷新
- 登出：服务端使 refresh token 失效。
- 刷新：使用 refresh token 获取新 access token。

### 4.5 安全底线
- 全链路 HTTPS。
- 密码仅哈希存储。
- 登录限流与失败锁定。
- 错误提示统一，避免账号枚举。

### 4.6 对应功能需求（FR）
- AUTH-FR-001：用户名密码注册。
- AUTH-FR-002：用户名密码登录。
- AUTH-FR-003：登录限流与失败锁定。
- AUTH-FR-004：登出与 token 刷新。

## 5. 大模块二：AI 调解模块（核心，P0）

### 5.1 功能目标
- 建立冲突处理闭环：私有梳理 -> 双方确认 -> 中立裁判 -> 复盘沉淀。

### 5.2 核心流程
1. A 私有分析阶段（不落共享数据）。
2. A 确认事实并冻结为 Snapshot_A，事件进入 `waiting_b`。
3. 推送给 B，B 选择同意或不同意。
4. 生成 JudgeResult，事件进入 `judged`。
5. 双方查看固定结果，后续可继续复盘聊天。

### 5.3 A 私有分析阶段
- A 点击"聊天分析"。
- A 与 AI 对话，AI 仅做文本整理和观点抽取。
- 该阶段数据仅在后端临时缓存会话中使用，不写共享 Event / Snapshot / JudgeResult。

### 5.4 A 确认事实（Commit/Freeze）
- A 点击"对，基本是这样"。
- 后端执行：
  1. 从当前临时分析会话生成结构化事实。
  2. 事务内创建 Event。
  3. 创建 Snapshot_A（冻结，不可修改）。
  4. 持久化保存，写入 `event_state_logs`（见 `repos/audit_repo.py`）。
  5. Event.status 置为 `waiting_b`。
- 该行为定义为一次明确的 commit/freeze。

### 5.5 发送给 B
- B 打开软件后可在关系摘要中发现当前待处理事件；进入后默认只读查看 Snapshot_A。
- B 有两种分支：
  1. 同意：`b-agree` 校验 `agree=true` 后执行 `judge(snapshot_A, inferred_snapshot_B)`，生成 JudgeResult，Event.status=`judged`。同时自动创建 review + calendar_entry（见 `services/review_service.create_review_from_judge`）。
  2. 不同意：B 先进入自己的私有分析会话，确认后生成 Snapshot_B，再 `judge(snapshot_A, snapshot_B)`，Event.status=`judged`。同样自动沉淀 review + calendar。

### 5.6 查看结果
- 用户点击"分析结果"时，系统直接读取落库 JudgeResult。
- 不实时调用 AI，确保结果稳定、可复现。

### 5.7 后续自由聊天
- 双方可继续与 AI 聊复盘、追问、求建议。
- 后续聊天不得修改已冻结 Snapshot 与已生成 JudgeResult。

### 5.8 记忆实现
采用"检索式上下文拼接"：每次请求都由后端实时构建上下文（见 `utils/context_builder.py`）。

`build_context(user_id, event_id)` 必含：
1. 最近对话（短期记忆，6-10 轮）。
2. 事实快照（snapshot_A/snapshot_B，罗生门原则：分别读取，禁止合并）。
3. 历史记录（吵架日历，可逐步接入）。
4. 裁判结果（judge_result）。
5. 当前输入（current_message）。

Prompt 模板骨架：
- 系统角色：客观中立，不偏袒。
- 历史记录。
- 事实背景（Snapshot）。
- 裁判结果。
- 最近对话。
- 当前问题。

### 5.9 成本与性能策略
- 最近对话 <= 10 条。
- snapshot <= 2 条。
- judge <= 1 条。
- 单次调用总上下文 <= 1500 tokens。

### 5.10 对应功能需求（FR）
- MED-FR-001：A 私有分析不落共享数据。
- MED-FR-002：A 确认即生成 Snapshot_A（不可变）。
- MED-FR-003：B 同意/不同意双分支处理。
- MED-FR-004：生成并落库 JudgeResult。
- MED-FR-005：查看结果不触发实时 LLM。
- MED-FR-006：后续对话支持基于历史上下文复盘。

## 6. 大模块三：吵架日历模块（P1）

### 6.1 功能目标
- 将冲突复盘以日历方式沉淀，支持关系长期改进。

### 6.2 功能设计

## 7. 大模块四：互动模块（P2，后续）

### 7.1 功能目标
- 提供低冲突沟通辅助，但不抢占主流程入口。

### 7.2 功能设计
- 小精灵代转达：用户输入诉求，系统润色后送达。
- 过激语言劝阻：识别高风险表达并提示改写。

### 7.3 对应功能需求（FR）
- IM-FR-001：代转达。
- IM-FR-002：过激语言拦截与柔化。

## 8. 验收标准（UAT）
- A 未确认前，数据库不得写入 Snapshot_A。
- A 确认后，Event 状态必须变更为 `waiting_b`。
- B 同意或提交 Snapshot_B 后，必须可生成 JudgeResult。
- 分析结果页面重复打开不得触发新判定。
- 后续复盘对话可引用已确认 Snapshot 与 JudgeResult。
- 日历可按日期查看并编辑复盘内容，双方可见。

## 9. 非功能要求
- 一致性：状态更新和关键写入同事务。
- 可追溯：保留状态变更日志与关键 AI 调用日志。
- 权限隔离：按 relationship_id 强约束读写范围。
- 成本可控：token 上限和降级策略必须生效。
